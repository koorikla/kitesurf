## 3. T0.3: kite loop records, independent of `bLooping` (PR2)

### Approach

Integrate the kite's **own per-step heading turn** (`TurnRad`, `KiteComponent.cpp:812`), which today only counts while `bLooping` is set (:814-817). Feed it to a pure tracker that lives in the kite.

Why this and not differencing `GetKiteHeading()` per frame, as tricks.md suggests: the per-step turn is exact. Differencing headings also picks up the projection of the heading as the kite moves and the slack-line re-orientation (:743-ish branch), which are not turns.

Putting the tracker in the kite means it also runs under `Kite->UpdateKite` alone, so `FStandingFixture` tests work.

### New file: `Public/KiteLoopTracker.h` (+ `Private/KiteLoopTracker.cpp`)

```cpp
USTRUCT(BlueprintType) struct FKiteLoopRecord { GENERATED_BODY()
  UPROPERTY(BlueprintReadOnly) int32 Index = -1;           // monotonic per kite
  UPROPERTY(BlueprintReadOnly) int32 Direction = 0;        // +1 right/clockwise seen from the rider (same sign as GetTurnDeg), -1 left
  UPROPERTY(BlueprintReadOnly) float StartTimeSeconds = 0; // kite sim time
  UPROPERTY(BlueprintReadOnly) float DurationSeconds = 0;
  UPROPERTY(BlueprintReadOnly) float TurnDeg = 0;          // magnitude reached in this record
  UPROPERTY(BlueprintReadOnly) bool  bCompleted = false;   // reached 360
  UPROPERTY(BlueprintReadOnly) bool  bKiteCrashed = false;
  UPROPERTY(BlueprintReadOnly) float StartElevationDeg = 0, MinElevationDeg = 90, PeakTensionN = 0;
  UPROPERTY(BlueprintReadOnly) float RiderZAtStartCm = 0;
  UPROPERTY(BlueprintReadOnly) int32 RiderTravelSide = 0;  // sign of rider velocity on crosswind-right at start (for contra, T2.4)
};
struct FKiteLoopSample { float TimeSeconds; float TurnDeg; float ElevationDeg; float TensionN;
                         float RiderZCm; FVector RiderVelocity; FVector DownwindDir; bool bFlying; bool bCrashed; };
struct FKiteLoopTrackerSettings {   // all estimates
  float StartTurnDeg = 30;          // same-sign turn before a run counts
  float ReverseToleranceDeg = 45;   // counter-turn from the run's peak that ends it
  float StallRateDegPerS = 20;      // below this...
  float StallSeconds = 0.6f;        // ...for this long ends a run (a kite parked or travelling)
  float MinPartialDeg = 180;        // an unfinished run this long is kept (S-loop halves, heli loop)
  int32 MaxRecords = 64; };
class KITESURF_API FKiteLoopTracker {
public:
  void Step(const FKiteLoopSample&);
  void CancelRun();                 // teleport/placement: drop without a record
  const TArray<FKiteLoopRecord>& GetRecords() const; int32 GetTotalRecorded() const;
  bool GetOpenRun(FKiteLoopRecord& Out) const;   // provisional, for jump ends and the ticker
  int32 GetRunDirection() const; float GetRunTurnDeg() const;
  FKiteLoopTrackerSettings Settings;
};
```

### Algorithm

- **Pending phase.** Turn accumulates into a pending value. The pending start time and elevation are reset whenever |rate| < `StallRateDegPerS`. When |pending| ≥ `StartTurnDeg`, a run opens with the pending start as its start.
- **Running.** Add `Turn × Dir`. Each time the run crosses a multiple of 360, emit a completed record; the next loop starts at that crossing.
- **Run end.** A run ends when any of these happens:
  - peak − current > `ReverseToleranceDeg` (an opposite run starts pending at that counter-turn);
  - the stall rule fires;
  - `bCrashed` is set (this also marks `bKiteCrashed`).
- **Remainder.** When a run ends with a remainder ≥ `MinPartialDeg`, emit an incomplete record.
- **Per-record extremes.** Min elevation and peak tension are tracked per record.

```cpp
  UPROPERTY(BlueprintReadOnly) float StartSinceTakeoffSeconds = 0, StartSinceApexSeconds = 0; // negative = before apex

};
USTRUCT(BlueprintType) struct FJumpRecord { GENERATED_BODY()
  UPROPERTY(BlueprintReadOnly) int32 Index = -1;  EJumpOutcome Outcome;  bool bPopped;
  UPROPERTY(...) float TakeoffTimeSeconds, ApexTimeSeconds, LandingTimeSeconds, AirtimeSeconds;   // board sim time
  UPROPERTY(...) FVector TakeoffLocation, LandingLocation;  float TakeoffSpeedCmS;
  UPROPERTY(...) float ApexHeightCm, DistanceCm;

  UPROPERTY(...) float TakeoffTensionN, PeakTensionN, MinKiteElevationDeg;
  UPROPERTY(...) TArray<FJumpLoop> Loops;
  int32 CountCompletedLoops() const;
};
struct FJumpRecorderInput {              // one snapshot per sim step
  float BoardTimeSeconds; EBoardState State; bool bCrashing;
  int32 TakeoffCount, JumpCount, ResetCount; bool bLastTakeoffPopped; float LastTakeoffTimeSeconds;
  FVector Location, Velocity; float TensionN, KiteElevationDeg, KiteTimeSeconds;
  float LastApexCm, LastApexTimeSeconds, LastAirtimeS, LastDistanceCm, LastLandingG, LastSinkRateCmS, LastLandingAngleDeg; bool bLastLandingClean;

class KITESURF_API FJumpRecorder {
public:
  /** True when a record was finalised this step (OutRecord filled). */
  bool Step(const FJumpRecorderInput& In, FJumpRecord& OutRecord);
  bool IsJumpOpen() const; const FJumpRecord& GetLive() const;

```

**Step logic:**
- **Take-off:** `TakeoffCount` changed → open a live record with the take-off time, location, speed and tension. Also note the kite time and the kite's loop count.
- **While open:** keep the peak tension and the minimum kite elevation.
- **Landing or crash:** `JumpCount` changed → finalise from the `Last*` fields.
  - The outcome is `Landed` when `bLastLandingClean`, otherwise `Crashed`.
  - Loops: every kite record whose time span overlaps [take-off, landing] in kite time, plus the open run if it is ≥ 180°. Each is converted to an `FJumpLoop`.
- **Reset:** `ResetCount` changed while open → drop the record.
- **Skip:** open, state no longer `Airborne`, not crashing and no `JumpCount` change → drop.
- **Landing with no take-off seen:** this happens in tests that call `SetBoardState(Airborne)`, such as `BoardMovementTests.cpp:525`. Ignore it.

Matching rules:
- The first row wins.
- More degrees than `BaseDegrees` adds a number (`Stem + " " + PassNumber`, or `Stem + PassNumber`), giving "KGB 5", "Slim 7", "315".
- A `Pop` with a pass becomes "Frontside 3" or "Backside 5".

**Big air naming** composes, in this order:
1. `[Double|Triple]`;
2. `[Early|Late]`;
3. one of `{Megaloop|Kiteloop|Contra loop|Heli loop|S-loop}`; 4 or more loops is "Kiteloop x4";
4. `[Double|Triple] {Back roll|Front roll|Backflip|Front flip}`;
5. `[Frontside|Backside] N` for a hooked spin of N = half turns × 180;
6. `[One-footer]`;
7. `[Board-off|Superman|Tic tac|Board pass|Board flip]`;
8. the grab name;
9. `[to blind|to toeside]`.

With no elements the name is "Straight air". Only the first word is capitalised.

**Fallback:** when no table row or composition fits, join the parts with " + ", capped at `MaxNamedParts` parts followed by "…". Example: "Back roll + backside 540 pass to blind".

**`GradeLanding`:** Crash if the board crashed; Stomped if yaw ≤ 20°, g ≤ 4 and kite elevation ≥ 45°; Sketchy if kite elevation < 45° or g > 8; Clean otherwise. Tilt joins in T1.5.

**`ScoreJump`:** Total = h^1.15 (h = apex in m) × (1 + E) × (1 + T) × Exec.
- **E (extremity), from `Record.Loops`:** Σ 0.5 × clamp(1 − minElev/60) × clamp(heightAtStart/apex), plus 0.3 if any contra loop or S-loop.
- **T (technicality):** the sum of the element table in 6.8.

The tracker computes the signature, name, family key, grade, score and repeat factor at finalise time and stores them in new `FJumpRecord` fields: `TrickName`, `FamilyKey`, `Grade`, `Score`, `RepeatFactor`. This PR touches `JumpRecord.h` and `TrickTrackerComponent.cpp`.

1. **§5 and T0.1 are stale.** The physics rework is merged; fixtures already call `Pawn->Tick`; `StepSimulation` exists. "Until that merges, the pawn's Tick calls it" is obsolete, so the tracker hooks into `StepSimulation` now. T1's dependency on physics items 1-2 is already met.

10. **"Stomped" (≤ 4 g) is unreachable for big jumps today** at 30 cm absorb (about 35 g), and the kite sits low at touchdown, so big landings grade Sketchy until phase 2 items 1-2 land.
