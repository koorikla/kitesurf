# KiteSurf

A kitesurfing game on Unreal Engine 5.8 (C++, Linux, Vulkan), being developed into a big
air game: very high jumps, kite loops, tricks and scoring.

## Where things are

| Path | What it holds |
| --- | --- |
| `Source/KiteSurf/` | The one runtime C++ module: wind, kite, board, pawn, HUD, tests |
| `Config/` | Engine and input configuration |
| `Content/` | Binary assets (Git LFS), generated by `scripts/editor/*.py` |
| `scripts/` | Build, test, run and package wrappers; use these instead of raw engine commands |
| `docs/ARCHITECTURE.md` | Units, public APIs and tick order |
| `docs/TASKS.md` | Roadmap and current phase |
| `docs/research.md` | Big air research and the candidate backlog with acceptance criteria |
| `docs/tricks.md` | Trick catalogue (big air, freestyle, strapless) and the trick implementation plan |
| `.agents/skills/` | Skills for working in this repository (index below) |

## Working rules

- Build and test before reporting work as done: `scripts/build.sh Development`, then
  `scripts/run-tests.sh -nullrhi`. Read the `Test Results:` line; a missing report does not
  fail the script.
- Every physics change comes with automation tests named `KiteSurf.<Area>.<Behaviour>`.
- Units: Unreal positions are centimetres; do physics in SI inside the simulation and
  convert once at the boundary. 1 knot = 0.5144 m/s.
- Assets are generated by scripts in `scripts/editor/`. Change the script, rerun it, and
  commit the script and the binary together.
- Say what was verified and how. "Seen in a `-game` run", "passes under `-nullrhi`" and
  "not checked" are different claims.
- Numbers in `docs/research.md` tagged *estimate* are tuning starting points, not
  requirements.

## Always merge to main

Work is finished only when it is on `main`. A pushed branch or an open pull request is not
done: other agents and task workspaces start from `main` and will not see it.

1. Branch from the latest `origin/main`.
2. Commit, push, and open a pull request against `main`.
3. Wait for CI (`build-and-test`) to pass. If it fails, fix it on the same branch.
4. Squash-merge the pull request and delete the branch:
   `gh pr merge <number> --squash --delete-branch`.
5. Confirm the change is on `origin/main` before reporting the task as done.

If the branch conflicts with `main`, update it from `origin/main`, resolve the conflicts,
and let CI run again. If you cannot merge (failing CI you cannot fix, a conflict you cannot
resolve safely, missing permission), say so plainly and name the branch and pull request;
do not report the task as done. Never push directly to `main` and never merge with CI red.

## Skills

Each skill is a folder under `.agents/skills/` with a `SKILL.md`. If your skill list does
not already show them, read the `SKILL.md` of the relevant skill before starting that kind
of work.

Project-specific:

| Skill | Use it when |
| --- | --- |
| `kitesurf-build-test` | Building, running tests, launching the game, packaging, reproducing CI |
| `kitesurf-automation-tests` | Writing tests; turning an acceptance criterion into a check |
| `kitesurf-editor-python` | Creating or changing levels, input assets or any `.uasset` |
| `kitesurf-big-air-sim` | Changing kite, board, wind, jump or landing physics |
| `unreal-water-queries` | Reading wave height and normals from the Water plugin |

Unreal Engine:

| Skill | Use it when |
| --- | --- |
| `unreal-cpp-gameplay` | Writing `UCLASS` / `UPROPERTY` C++, components, `Build.cs` |
| `unreal-enhanced-input` | Adding Input Actions, mapping contexts and bindings |
| `unreal-niagara` | Spray, wake and other particle effects driven from C++ |
| `unreal-packaging` | Cooking and packaging builds |

Game design and feel (engine-neutral; their code samples are Godot and Unity, so take the
method and write the Unreal version):

| Skill | Use it when |
| --- | --- |
| `game-feel` | Feedback on pop, landing and loops: shake, hit-stop, easing |
| `camera-systems` | Follow smoothing, framing rider and kite, camera jitter |
| `game-ui-ux` | HUD and menu layout, scaling, gamepad focus, event-driven HUD |
| `input-systems` | Action mapping, deadzones, buffering, rebinding, accessibility |
| `physics-tuning` | Fixed timestep, interpolation, stability |
| `audio-design` | Buses, ducking, variation for wind, line and water sound |
| `performance-optimization` | Profiling first, frame budgets, CPU against GPU |

Provenance and licences for the third-party skills are in `.agents/README.md`.
